# Contributori

Non serve conoscere tutto Antiskill. Scegli un problema piccolo o una competenza che già possiedi.

## Per competenza

| Profilo | Buoni punti di ingresso |
|---|---|
| Giocatore / utente | Rapporti, Qualità, idee di applicazione |
| Istruttore | Rapporti, Analisi, didattica, validazione scacchistica |
| Arbitro / organizzatore | Fonti, tornei, broadcast, Qualità |
| Storico / archivista | Conoscenza, Fonti, provenienza |
| Rust | Nucleo, Interoperabilità, Piattaforma |
| Python / dati | Rapporti, Ricerca, conversioni |
| Statistica | Ricerca |
| GUI / UX | Interoperabilità |
| Testing | Qualità e portabilità |
| Esperto di una federazione o sito | Fonti, Conoscenza |

## Per area

- **Nucleo** — parser, storage, identità, deduplica, indici, ricerca, prestazioni.
- **Ricerca** — protocolli, statistica, replicazioni, modelli umani.
- **Rapporti** — domande pratiche su giocatori, repertori, tornei e corpus.
- **Analisi** — engine, Syzygy, UCI e riuso dei risultati.
- **Fonti** — federazioni, sistemi torneo, broadcast, archivi.
- **Interoperabilità** — En Croissant, Scid, formati, script, API.
- **Conoscenza** — eventi, aperture, albi, rating list, storia.
- **Piattaforma** — job, cache, checkpoint, resume, esecuzione portabile.
- **Laboratorio** — prototipi delimitati.
- **Qualità** — test, fixture, documentazione, privacy, portabilità.

## Tre modi semplici per iniziare

### Segnala

Un bug riproducibile, una fonte utile, un caso limite o una lacuna documentale è già un contributo.

### Proponi

Per una nuova applicazione non serve progettare subito l'architettura. Spiega:

- il problema;
- chi ne beneficia;
- quali dati servirebbero;
- come immagini che Antiskill possa aiutare.

Il punto di integrazione si decide dopo. Vedi [Possibilità](POSSIBILITA.md).

### Costruisci

Scegli una issue piccola oppure apri una PR diretta per una correzione ovvia. Se il lavoro cambia formati persistenti, identità, rete o diritti delle fonti, apri prima una issue.

## Non serve Rust

Sono contributi di prima classe:

- verificare una fonte e i suoi diritti;
- descrivere un workflow reale;
- proporre un rapporto;
- costruire una fixture sintetica;
- testare Windows/macOS/Linux;
- revisionare un risultato scacchistico;
- migliorare testi ed esempi;
- classificare casi storici o federali;
- replicare un esperimento.

## Buona issue

Una buona issue dice almeno **cosa non funziona o cosa sarebbe utile**. Criteri di accettazione, area e soluzione tecnica possono emergere nella discussione: non devono diventare una barriera all'ingresso.

## Buona PR

Una buona PR è piccola, leggibile e verificabile. Non deve risolvere problemi vicini solo perché sono stati scoperti nello stesso momento.

Vedi [Contribuire](../CONTRIBUIRE.md).
